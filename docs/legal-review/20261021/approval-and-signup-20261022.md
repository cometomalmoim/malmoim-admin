# 문서 승인 및 회원가입 활성화 준비

운영진이 이 대화에서 개인정보 처리방침과 서비스 이용약관을 승인하고, 양 문서 시행일을 **2026-10-22**로 명시했습니다. 승인 전 초안의 파일·해시·manifest는 변경하지 않았습니다. 별도 `approval-20261022.json`에 승인 사실, 버전, 공개 변환, 미확정 사항을 기록했습니다.

## 반영 결과

- `/privacy`, `/en/privacy`: 승인 개인정보 처리방침 16개 조항과 표 4개.
- `/terms`, `/en/terms`: 승인 이용약관 18개 조항.
- 두 언어 모두 시행일·문서 버전·목차를 표시합니다. 가입 모달과 독립 페이지는 같은 정적 문서 객체를 사용하며 푸터의 언어별 링크도 유지합니다.
- 원문의 시행일 자리만 지정일로 바꿨습니다. 명시적으로 표시된 제7조의 내부 검토 메모 한 문단은 공개 본문과 분리하고 원본·승인 기록에 보존했습니다. 제7조 본문과 6개 고지 항목 등 조항·표·목록은 삭제하거나 확정 사실로 바꾸지 않았습니다. 내부 메모 분리가 국외 이전 등 미확정 사항의 해결을 의미하지 않습니다.
- 버전: `privacy-2026-10-22-v1`, `terms-2026-10-22-v1`, 가입 수집 안내 `signup-required-2026-10-22-v1`.
- 가입에 필수·미체크 약관 동의와 개인정보 처리방침 전문 열람을 적용했습니다. 원문의 계약 체결·이행 근거를 반영한 필수 항목 안내를 제공하고, 개인정보 처리방침 자체에 대한 별도 필수 동의를 임의로 만들지 않았습니다.
- 필수 이메일·비밀번호·닉네임·생년월일·한국어/영어 수준을 유지합니다. 처리 목적과 별도 고지가 미확정인 선택정보는 현재 가입 UI에서 수집하지 않습니다. 기존 선택정보 검증/입력 컴포넌트는 보존했지만 현 가입 설정에서 제외하고, 서버도 이 설정을 우회한 선택정보 저장 요청을 거절합니다.

## 회원가입 활성화 조건

기존의 무조건 `null`인 앱 설정을 승인 문서에서 파생되는 설정으로 바꿨습니다. 다음 조건을 모두 충족하면 실제 가입 버튼과 약관 체크박스를 활성화합니다.

1. 요청 시점의 한국 날짜가 양 문서 시행일인 2026-10-22 이상.
2. 서버의 문서·수집 안내 버전과 정책 버전이 정확하게 일치.
3. Supabase의 `member_registration_v2_ready` 읽기 응답이 같은 버전과 계약 기반 처리 설정을 반환.

화면 렌더링과 서버 가입 처리에서 각각 확인합니다. 준비되지 않은 경우 화면은 이유를 한 번 안내하고, 입력 검사 시에는 개인정보 필드를 서버로 전송하지 않습니다. 화면을 우회해 서버 액션을 호출해도 시행일·버전·DB 확인을 통과해야 계정이 생성됩니다. 닉네임 중복, 19세, 비밀번호, 세션 검증, 원자적 프로필·언어·약관 증빙 저장과 실패 처리 흐름은 유지했습니다.

**운영 사이트 가입이 지금 활성화된 것은 아닙니다.** 배포 및 운영 DB 변경 금지 지시를 유지했으며, 실제 프로젝트에 필요한 RPC와 승인 정책 행이 설치되어 있는지 확인하거나 변경하지 않았습니다. 지정일 전이므로 로컬 화면도 아직 시행 안내를 표시합니다.

## 운영 적용을 위한 준비물과 절차

`supabase/drafts/20261022_member_registration_activation_review.sql`을 수동 검토용으로 생성했습니다. 웹사이트와 동일한 한영 문서·수집 안내 스냅샷을 저장하고, 한국 날짜 기준 시행일부터 기존 v2 저장 경로가 준비 응답을 반환하도록 합니다. 실제 SQL 실행은 하지 않았습니다.

후속 운영 적용은 별도 승인 범위에서 다음 순서로 진행해야 합니다.

1. 아래 미확정 운영 정보를 확인합니다. 문서 승인 사실과 실제 이행·고지 정보 확인은 별개입니다.
2. 운영 DB의 기존 테이블·함수·권한·현재 활성 정책을 읽기 전용으로 점검합니다. `20261016`, `20261017`, `20261020` 파일은 과거 생성 초안이므로 그대로 재실행하면 안 됩니다. 특히 현재 DB에 nickname/acceptance 확장이 없다면 기존 메타데이터에 맞춰 추가 변경을 별도로 검토해야 합니다.
3. Supabase Auth의 신규 가입 허용, 비밀번호 정책, 이메일 Confirm 설정, SMTP/알림 설정을 직접 확인합니다. 메일을 쓰지 않는 운영 정책과 실제 설정을 일치시켜야 합니다. 코드에서 원격 Auth 설정을 확인하거나 변경한 것은 아닙니다.
4. 준비된 경우 활성화 SQL을 검토하여 적용합니다. 스크립트는 사전 조건, 기존 활성/동일 버전 정책, 기존 직접 프로필 쓰기 권한을 검사하고 불일치하면 중단합니다. 기존 정책을 덮어쓰거나 회원/게시물을 수정하지 않습니다.
5. 이 코드의 테스트를 재확인하고 명시적인 배포 절차를 진행합니다. 배포 후 별도로 승인된 테스트 계정으로 실제 가입, 동의 증빙, 로그인 및 작성자 표시를 확인합니다. 이번 로컬 검증에서는 실제 계정 생성·메일 발송을 하지 않았습니다.
