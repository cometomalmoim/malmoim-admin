# A조 신청자 운영 관리

1. 문제사항: 신청자 목록은 읽기 전용으로 운영진의 추가·수정·선발·입금 확인·조건별 조회가 불가능했다.
2. 개선 경험: 신청자 직접 추가와 상세 수정, 선발 상태, 입금 수동 확인, 출생연도·국적·내부 메모를 연결하고 서버 검색/필터/페이지 이동을 추가했다.
3. 진행 과정: 기존 9기/할로윈 응답 구조 확인 → 운영 관리 보조 테이블/수동 접수/감사 기록 → 관리자 전용 저장 함수 → 목록 필터/상세 폼 → 테스트/빌드 → 배포 후 가상 데이터 확인.
4. 측정: 입력 테스트 3개 통과. lint·Webpack 운영 빌드 통과. DB 11조건(추가/수정/조회/감사기록/동시수정충돌/이벤트격리/중복/온라인-수동중복/비관리자조회/비관리자수정/익명수정금지) 통과. DB 테스트 변경은 모두 rollback. 웹 검증과 실운영 효과는 별도 기록. 시간 감소 미측정.
5. 어려움과 해결: 기존 질문/개인정보 동의를 바꾸지 않기 위해 관리 정보와 수동 접수를 분리했다. 저장 함수의 변수·열 이름 충돌을 가상 테스트에서 발견해 변수명을 구분하고 재검증했다.
6. AI 활용: 업무 항목을 서버·DB·화면에 반영하고 실제 데이터 변경 없이 권한·충돌·중복 경계를 검증했다.
7. 포트폴리오: 이벤트별 신청자 편집과 선발·입금 상태 관리, 개인정보 최소 조회 및 필터를 구현하고 가상 데이터로 저장·충돌·권한 경계를 검증했습니다.
8. 자소서: 읽기 전용 신청자 화면의 운영 제약을 발견하고 정보 수정과 상태·입금 기록을 담당했습니다. 기존 신청 정보를 보존하는 구조를 설계하고, 동시 수정 시 덮어쓰지 않도록 버전 검증과 변경 이력을 추가했습니다.

선발 합격과 참가 확정을 구분한다. 입금/환불은 운영진 수동 기록이며 결제·송금·환불·문자 전송은 실행하지 않는다. 출생연도/국적은 관리자에서만 입력하고 공개 폼에 추가하지 않는다. 미확인 값은 빈값으로 보존한다. 생일 전체를 새로 수집하거나 나이를 추정하지 않는다. 수동 추가에 접수 경위를 필수 기록하며 개인정보/마케팅 동의를 대신 생성하지 않는다. 저장 실패 시 입력 유지, 충돌 시 최신 목록 확인을 요구한다.
