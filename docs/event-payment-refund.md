# 참가비·납부·환불 기록 적용 안내

이 변경은 실제 송금 기능을 포함하지 않습니다. DB 적용·main 병합·배포는 별도 확인 전까지 보류합니다.

## SQL 선택과 순서

기존 신청자 관리 `010_applicant_management.sql`과 이미 적용된 `011_participation_history.sql`을 보존합니다. 기존 참여 이력 테이블·뷰·RPC를 재정의하지 않습니다. 아래 신규 파일만 순서대로 검토합니다.

1. `012_event_fee_settings.sql`: 기존 이벤트 행에 참가비와 입금 안내 필드 추가. 고정 금액·초기 금액 주입 없음.
2. `013_applicant_payment_management.sql`: 기존 신청자 관리 테이블·목록 뷰·저장 RPC에 확인 대기 및 납부 확인 기록 추가.
3. `014_applicant_refund_management.sql`: 환불 기록·감사 연결·전용 RPC·일반 납부 수정 보호 트리거 추가.

혼합 초안 `011_event_payment_refunds.sql`은 적용 대상이 아닙니다. 폴더 전체 SQL이나 검증용 SQL을 일괄 실행하지 않습니다. 이번 신규 SQL은 미적용 상태를 전제로 번호를 정리했으며, 실제 DB의 컬럼·함수·적용 이력은 별도 확인해야 합니다. 특히 환불 SQL은 재실행용 스크립트가 아닙니다.

## 상태와 기존 데이터

- 참가비는 `recruitment_events.fee_amount_krw` 한 곳에 저장합니다. 빈 금액은 미정, 0은 무료입니다.
- 기존 `unknown`, `unpaid`, `paid`, `refunded` 상태를 유지하며 `pending_confirmation`을 추가합니다.
- `paid` 진입 시 서버 관리자 ID·시간을 기록합니다. `paid` 유지 시 확인 기록을 보존하고 다른 상태로 전환하면 현재 확인 기록을 비웁니다. 기존 데이터의 빈 확인 기록을 추정해 채우지 않습니다.
- 환불 요청·승인·거절은 납부 상태를 유지합니다. 승인 후 관리자가 외부 송금 완료와 실제 금액을 확인해 완료를 기록하면 동일 트랜잭션에서 `refunded`로 변경합니다.
- 일반 신청자 수정으로 `refunded` 진입·해제는 차단합니다. 환불 상태 유지 시 일반 정보 수정은 가능합니다. 기존 환불 데이터에 상세 기록을 생성하지 않습니다.
- 진행 중 요청은 하나로 제한하고 완료된 환불을 재처리하지 않습니다. 이 단계는 신청자당 완료 기록 하나를 허용하며 분할·반복 환불은 지원하지 않습니다.

## 검증 범위

Node 테스트는 참가비·납부·환불 검증과 서버 액션·조회 경계, 참여 이력 링크가 포함된 통합 목록을 확인합니다. 운영 DB에 연결하지 않습니다.

`supabase/tests/applicant_payment_management.sql` 및 `applicant_refund_management.sql`은 010·013·014가 적용된 별도 테스트 DB에서 명시적으로 실행할 검증 스크립트입니다. 요청·승인·처리의 납부 상태 유지/전환, 일반 수정 차단·프로필 수정 보존, 감사·권한·수정 충돌을 확인하고 롤백합니다. 실행에는 별도 승인이 필요하며 이 작업에서는 실행하지 않습니다.

배포 전에 실제 DB에서 SQL 적용·RLS·동시 처리·전체 롤백과 Supabase 관계 조회를 확인해야 합니다. 신규 스키마 없이 UI만 배포하면 조회·저장에 실패할 수 있으므로 적용 순서를 함께 검토합니다.

로컬 `previews/event-fee/`와 혼합 초안은 커밋·배포 대상에서 제외합니다. 기존 stash와 Documents 백업은 유지합니다.
