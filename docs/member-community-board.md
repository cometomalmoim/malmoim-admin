# 회원 커뮤니티 게시판 구현·DB 검토 보고서

작성일: 2026-10-17. 현재 브랜치: feat/operations-juho (이번 작업 시작 시 확인한 AGENTS.md 기준).
상태: 앱 코드/검토 SQL/로컬 테스트 구현. 운영 DB·원격 Auth 설정 미변경. commit/push 미실행.

## 1. 작업 전 분석

- /board와 /en/board는 공개 [slug] 준비 화면이었다.
- /admin/member-board는 등록된 메뉴지만 실제 구현은 공통 안내 화면이었다.
- 기존 internal_board_posts/comments 및 관리 함수는 관리자 내부 업무용이다. 기존 작성자 표시가 이메일을 사용할 수 있어 이를 공개 게시판으로 전환하지 않았다.
- 기존 관리자 /login, admin_users, getAdminAccess와 Supabase SSR 클라이언트를 재사용했다.
- 일반 회원 프로필 SQL은 초안이며 실제 적용 여부는 확인되지 않았다. 공개 닉네임 테이블/확정 정책도 찾지 못했다.
- 운영 메타데이터 접근 도구가 없어 실제 DB 객체/정책/적용 이력은 확인하지 않았다. 파일만으로 운영 스키마를 확정하지 않는다.

## 2. 사용자 게시판

- /board, /board/new, /board/[id], /board/[id]/edit 및 대응 /en 경로.
- 카테고리는 공지사항(notice), 자유게시판(free), 언어 질문(question)만 사용한다.
- 얇은 구분선의 표형 목록에 번호·카테고리·제목·별칭·한국 날짜·조회수·댓글 수를 표시한다. 본문 미리보기는 덜어내고 모바일에서는 간결한 세로 목록으로 전환한다.
- 카테고리와 무관하게 고정 게시글이 먼저, 나머지는 최신순이다. 여러 개 고정할 수 있고 고정 그룹 안에서도 작성일 최신순이다. 목록 20개/페이지, 댓글 30개/페이지.
- 로그인 회원의 일반 글 작성/수정/소프트 삭제, 공개 댓글 조회와 회원 댓글 CRUD, 신고를 연결했다.
- 실제 목록이 비어 있을 때만 빈 상태를 표시한다. DB 함수가 없거나 연결 실패 시 별도 준비/연결 안내를 표시한다.
- DB 미준비 시 로그인한 작성자에게도 저장 가능한 것처럼 폼을 제공하지 않는다.
- 본문은 React 일반 텍스트로 렌더링한다. HTML 삽입/실행, 자동 번역, 외부 에디터 라이브러리는 없다.

## 3. 관리자 게시판

- 기존 ProtectedAdmin 인증 검사 뒤 /admin/member-board를 연결한다.
- 기존 AdminShell·사이드바를 사용하며 기존 내부 게시판은 유지한다.
- 전체 글/숨김/미처리 신고 수, 상태·카테고리·검색·기간·공개 작성자 별칭·고정 여부 필터, 관리 테이블을 제공한다.
- 공지 작성/수정/소프트 삭제, 모든 카테고리의 고정·해제, 일반 글·댓글 숨김/복구, 신고 검토/완료 처리를 제공한다.
- 관리자 화면도 사용자와 같은 board_posts/comments 데이터를 사용한다.
- 관리자는 타인의 일반 글·댓글을 재작성할 수 없다. 본인 일반 글의 수정은 작성자용 화면으로 연결한다.
- 신고 당시 원문, 사유, 대상 및 처리 기록을 관리자에게 제공한다. 사용자 화면에는 신고 수·신고자·운영 기록을 제공하지 않는다.
- 삭제된 원문/댓글은 공개하지 않으며 관리자용 조회에만 남긴다. 작성자 삭제를 관리자 복구로 되돌리지 않는다.

## 4. 게시글 수정·삭제 권한

- UI: 조회 RPC에서 생성한 can_edit만 사용하며 작성자 일반 글 또는 관리자 공지에만 수정 기능을 표시한다.
- 서버: getUser로 인증을 확인하고 member_board_can_change로 소유권을 재검증한다. 클라이언트의 작성자 UUID/역할 값은 저장에 사용하지 않는다.
- DB: 직접 UPDATE RLS는 공개 상태인 본인 일반 글에만 허용한다. WITH CHECK로 공지 전환/소유권 이동을 차단한다.
- INSERT는 소유자와 공개 상태, 카테고리를 검사한다. 새 작성자 ID는 auth.uid(), 별칭은 DB가 결정한다.
- title/content/category만 직접 수정 권한을 부여한다. author_id/id/author_name/created_at/submission_id 보호 트리거도 둔다.
- status/is_pinned/view_count/updated_at은 일반 회원의 직접 변경 컬럼 권한이 없다.
- 물리 DELETE 권한은 부여하지 않는다. 검증된 저장 RPC만 본인 글의 status를 deleted로 바꾼다.
- 저장 함수는 소유권과 updated_at 버전을 row lock 아래에서 다시 확인한다. 오래된 수정 요청을 거부한다.
- 관리자 숨김/복구와 공지 관리 권한은 별도로 실제 admin_users를 검사하며 운영 이력을 같은 트랜잭션에 기록한다.

## 5. 댓글

- 공개 게시글의 공개 댓글만 비회원에게 보인다. 숨김/삭제 부모의 댓글은 검색과 직접 SELECT에서도 제외한다.
- 회원만 등록 가능하고 수정·삭제는 작성자만 가능하다. 서버와 DB에서 다시 확인한다.
- 댓글 최대 2,000자, 글 제목 200자, 본문 20,000자. 공백·탭·줄바꿈뿐인 입력은 서버와 DB에서 거부한다.
- 댓글의 post_id/author_id/작성 시각 등은 이동·변경할 수 없다.
- 인라인 수정은 원문을 채우고 취소 시 복원한다. 저장 오류 시 입력을 유지하고 처리 중 중복 제출을 막는다.
- 관리자도 타인의 댓글 내용을 수정하지 않으며 사유를 남겨 숨김·복구한다.
- 대댓글은 이번 범위에 포함하지 않았다.

## 6. 검색·키워드·조회수

- q/category/scope/period/page와 관리자 status를 URL로 관리한다.
- 제목+본문+댓글 / 제목 / 공개 별칭 / 댓글 범위를 제공한다.
- 댓글 검색은 EXISTS를 사용하므로 같은 글에 여러 댓글이 일치해도 게시글 한 건으로 반환한다.
- 전체기간/최근 1일/1주/1개월/3개월/1년의 6개 기간을 제공하며 게시글 created_at에 적용한다. 월/분기는 DB 달력 interval이다.
- 문자열 포함 검색은 바인딩된 JSON과 정적 SQL의 strpos를 사용한다. SQL 문자열 조립이나 사용자 wildcard 실행은 없다.
- 핫 키워드는 최근 7일의 최신 공개 게시글 최대 500개 제목·본문에서 집계한다.
- 소문자화·구두점 분리 후 한국어/영어의 제한된 안전 단어 목록과 일치한 단어만 사용한다. 조사·불용어와 임의 이름·전화·이메일·욕설은 인기어로 내보내지 않는다.
- 같은 글의 반복 단어는 한 번만 세며 실제 집계 결과가 없으면 키워드를 만들지 않는다.
- 형태소 분석/자동 추천/외부 서비스는 없다. 조사 붙은 단어나 안전 목록 밖 단어는 집계하지 않는 보수적인 첫 버전이다.
- 조회수 기준은 로그인 회원당 게시글별 한국 날짜 하루 1회다. 익명 방문은 집계하지 않고 IP를 저장하지 않는다. 중복 키로 새로고침·React 재실행을 방지한다.
- 조회수 갱신만으로 수정 버전을 바꾸지 않는다. 화면에도 집계 기준을 title 안내로 제공한다.

## 7. DB/RLS 검토 SQL

### 파일

- supabase/drafts/20261017_member_board_review.sql
- supabase/tests/member_board_access.sql
- tests/community-board-db.mjs (실제 SQL 적용/권한 회귀 테스트)

기존 번호 중복을 피하기 위해 날짜 기반 drafts 파일을 사용했다. 운영 적용 번호/순서는 DB 담당자가 실제 이력과 객체 이름을 확인한 후 별도로 정한다.
새 초안은 이름 충돌 시 실패하도록 IF NOT EXISTS나 기존 테이블 덮어쓰기를 사용하지 않는다.

### 테이블

| 테이블 | 목적 |
| --- | --- |
| board_posts | 글·공지·작성자 내부 UUID/공개 별칭·상태·고정·수정 시각·조회수 |
| board_comments | 글별 댓글·작성자·상태·수정 시각 |
| board_reports | 대상별 신고자·사유·신고 당시 원문·검토 상태 |
| board_moderation_logs | 처리 관리자 UUID·대상·종류·사유·DB 생성 시각 |
| board_aliases | Auth UUID와 무작위 공개 별칭의 비공개 연결 |
| board_view_days | 회원별 게시글 일일 열람 중복 방지, 비공개 |

- 공개 별칭은 Member- + 무작위 코드다. 이메일/전화/실명/Auth UUID로 별칭을 만들지 않는다.
- 프로필 없는 기존 Auth 사용자도 사용할 수 있다. 기존 회원 프로필/행사 사람 데이터를 자동 연결하지 않는다.
- 모든 신규 테이블은 ENABLE/FORCE RLS를 사용한다.
- 공개 조회는 안전한 JSON RPC와 제한된 컬럼만 허용한다. author_id 등 인증 UUID는 공개 응답에서 제외한다.
- 신고·운영 기록은 관리자 SELECT 정책만 허용하고 앱 역할의 직접 쓰기를 회수한다.
- 저장/조회 함수는 SECURITY DEFINER + 빈 search_path + 객체 한정 + 최소 EXECUTE 권한을 사용한다. 일반 회원이 admin 매개변수를 위조해도 거부한다.
- 함수 소유자는 검토된 BYPASSRLS migration owner(일반적으로 Supabase postgres)가 필요하다.
- 서비스 역할 키를 앱/브라우저에 추가하지 않았다.
- 글/댓글 생성 nonce를 사용자별 UNIQUE로 묶어 같은 요청 재시도가 중복 저장되지 않게 한다.
- 회원별 transaction advisory lock과 행 잠금, 버전 확인을 사용한다. 신규 글은 분당 10개, 댓글은 분당 50개 상한을 DB에서도 검사한다. 운영 전 수치 검토가 필요하다.
- 회원 소프트 삭제는 댓글/신고/운영 기록을 물리적으로 연쇄 삭제하지 않는다.
- auth.users FK는 기본 NO ACTION이다. 탈퇴/Auth 계정 삭제를 막을 수 있으므로 익명화·보관·삭제 정책과 함께 반드시 DB 총괄이 검토해야 한다.
- 기존 admin_users 구조 및 내부 게시판/Storage/행사/참여/자료 테이블은 수정하지 않는다.

### 로컬 적용 범위

PGlite 0.5.10을 Git 제외 work/sql에만 설치했다. 앱 package.json/lockfile은 변경하지 않았다.
테스트는 인메모리 DB에 실제 001_admin_users, 021/022/023 내부 게시판 SQL과 새 초안을 함께 적용한다.
Auth/Storage 스키마·역할은 테스트용 최소 모형이며 실제 Supabase JWT/Storage API와 동일한 통합 환경은 아니다.
운영 DB에 SQL을 적용하거나 테스트 Auth 계정을 생성하지 않았다.

## 10. 운영 DB 적용 전 필요한 작업

1. 실제 테이블·함수·정책 이름과 적용 이력, 동일 용도 기존 구조를 메타데이터로 확인한다.
2. 공개 별칭 운영 정책, 신고/삭제 원문 및 열람 중복 기록 보관 기간, 탈퇴·익명화·실삭제 절차를 확정한다.
3. 함수 소유자/권한/노출 스키마와 RLS를 검토하고 별도 테스트 Supabase에서 적용한다.
4. 기존 일반 회원 2명+관리자로 실제 JWT/SSR·작성자 공격·관리자 공지·숨김/신고·페이지 이동을 통합 검증한다.
5. 총괄 승인 후 운영 적용한다. 이 작업에서는 원격 적용하지 않았다.
6. 롤백은 쓰기 중지 후 데이터/의존성 백업·보존을 우선한다. 기존 내부/행사/Auth 데이터는 삭제하지 않는다. 새 객체 제거는 보관 정책과 FK 검토 후 담당자가 별도로 수행한다.

## 11. 다른 팀 영향과 인증

- 기존 관리자 /login→/admin, admin_users 서버 검사 및 내부 게시판 동작은 유지한다.
- 기존 Supabase SSR 클라이언트·설정과 공통 권한 검사 코드는 변경하지 않았다.
- 회원/댓글 로그인 유도에는 returnTo를 제공한다. 로그인 성공 시 검증된 /board/new 또는 게시글/수정 경로로 해당 언어에 맞게 복귀한다.
- 외부 URL, //호스트, 관리자 경로, 임의 쿼리/경로 이동은 returnTo로 허용하지 않는다. 관리자 로그인은 이 값과 관계없이 기존 /admin으로 이동한다.
- 기존 회원가입 차단 정책은 유지한다. 현재 신규 가입으로 테스트 계정을 만들 수 없으며 운영 계정을 생성하지 않았다.
- 일반 회원에게 관리자 등록이나 역할을 부여하지 않는다.
- 행사·신청·참여 이력·프로필·자료 데이터와 자동 병합/연결하지 않는다.
- 기존 내부 게시판 이미지 Storage 정책은 변경하지 않는다. 이번 커뮤니티에는 이미지 첨부를 추가하지 않았다.

## 12. 미구현·미검증 및 한계

- 운영 DB 적용/실제 Supabase JWT·SSR와의 인증 후 CRUD 통합은 미검증이다. 현재 실제 사이트에서 저장할 수 있다는 뜻이 아니다.
- 사용자 지정 닉네임, 닉네임 수정 기능은 없다. 안전한 자동 별칭을 임시 운영안으로 제공한다.
- 관리자에 의한 타인 일반 글/댓글 재작성, 영구 삭제 및 삭제된 글 강제 복구는 구현하지 않았다. 숨김·복구로 운영하며 실삭제 정책 확정이 필요하다.
- 대댓글·추가 카테고리·첨부 이미지·조회수순 정렬은 이번 1차 범위에서 제외했다.
- 핫 키워드는 안전 목록/최신 500개 집계여서 모든 자연어 표현을 분석하지 않는다.
- 게시글 본문에 사용자가 직접 기재하는 개인정보를 완전히 자동 판별하지는 않는다. 작성 안내와 개인정보 신고/관리자 숨김을 제공한다.
- 저장 결과가 네트워크 단절로 불명확하면 새 글로 반복 작성하지 말고 목록 확인/같은 nonce 재시도를 해야 한다. 앱은 nonce와 버전 검사를 사용하지만 분산 부하·운영 환경 동시성 전체 검증은 별도 필요하다.

### 최종 추가 검증

- 로그인 복귀 주소가 폼에 전달되고 서버에서 외부·관리자 주소를 거부함을 단위/브라우저로 확인했다.
- 인라인 댓글 취소 수락 시 원문으로 복원·편집 영역 닫힘, 취소 거절 시 입력 유지, 실패 재시도 시 동일 nonce 유지도 확인했다.
- 로컬 DB에 테이블/함수 기본 권한을 anon/authenticated에 넓게 부여한 조건을 먼저 만들고 새 SQL의 REVOKE·RLS가 이를 회수/차단하는지 확인했다.
- 줄바꿈·탭만 있는 글/댓글을 직접 RPC로 보내도 DB 제약이 거부한다.
- 최종 빌드·린트·149개 단위 테스트·로컬 DB 시나리오 모두 통과했다. 실제 Supabase 운영 적용/인증 통합은 여전히 미검증이다.

### DB/RLS 변경 이유

이전 초안에는 `is_pinned`가 notice 카테고리에만 허용되는 제약이 있었다. 이를 제거하고 관리자 검사 후 고정 값을 변경하는 기존 RPC를 재사용한다. 일반 회원에게 is_pinned 컬럼 수정 권한을 부여하지 않는다. 본인의 고정된 일반 글도 제목/본문/일반 카테고리를 수정할 수 있도록 UPDATE 정책의 `not is_pinned` 제한을 제거했고, 고정 상태는 그대로 보존된다. 고정 글의 본인 삭제 시에는 고정도 해제된다. 공지 작성은 계속 관리자만 허용한다.

관리자 목록의 고정 버튼은 숨겨진 요청 값에 대상 UUID·현재 수정 버전·새 고정 값·처리 사유를 보낸다. 서버에서 getUser/admin_users를 재검증하고 DB에서 행 잠금·관리자 권한·수정 버전을 다시 검사한다. 처리 후 공개 한영 게시판과 관리자 경로를 재검증한다. 클라이언트 값만으로 관리자 권한을 판단하지 않는다.

## 14. 실제 DB 연결 진단 및 적용 승인 준비

2026-10-17 후속 진단·수정·151개 테스트 결과·적용 전 메타데이터 검사와 데이터 보존 롤백은 [member-board-activation.md](member-board-activation.md)를 참고한다. 원격 Auth는 응답하지만 게시판 REST 객체/함수는 스키마 캐시에서 찾지 못했다. 운영 SQL은 실행하지 않았고 운영 활성화는 승인 대기 상태다.
