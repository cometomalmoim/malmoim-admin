## 입력 및 검증

- 이메일을 로그인 ID로 사용한다. 별도 username 필드는 없다.
- 비밀번호와 확인값 일치·표시 전환을 제공한다. 비밀번호는 정규화된 프로필 결과에서 제외한다.
- 화면의 비밀번호 8~128자 기준은 임시값이다. 실제 Supabase 길이·필수 문자·유출 비밀번호 정책을 확인한 뒤 활성화해야 한다.
- 국적은 249개 ISO 3166-1 alpha-2 코드와 한국어 표시명을 사용한다.
- 전화번호는 국가번호 선택/직접 입력과 번호를 분리한다. 현재 검증은 기본 문자·길이 형식 검사이며 실제 국가별 번호 유효성·소유권 확인은 하지 않는다. 국가별 앞자리 0 처리·최종 정규화 정책은 저장 연결 전에 확정한다.
- 성별 저장값은 female/male/undisclosed만 허용한다.
- 날짜 유효성·윤년·한국 시간 기준 미래 날짜를 검사한다. 나이 제한 정책은 임의로 추가하지 않았다.
- 한국어는 KOREAN_LANGUAGE_LEVELS의 none/basic/conversational/fluent/native 5단계, 외국어 신규 입력은 FOREIGN_LANGUAGE_LEVELS의 basic/conversational/fluent/native 4단계를 사용한다.
- 외국어 목록은 국가 목록과 별도로 확장 가능하며 한국어를 제외한다.
- 외국어 1~5개·중복·언어 코드·각 실력을 공통 검증한다. UI는 고유 행 ID와 함수형 상태 변경으로 중간 삭제 후 다른 값과 최대 개수를 보존한다.
- 개인정보 동의 검증은 공통 검증기의 기본 필수 조건이다. 현재 로컬 입력 확인만 requireConsent:false로 실행하며, 동의를 받았다고 기록하지 않는다.
- **실제 가입 서버 처리는 아직 없다.** 향후 서버 Action에서도 공통 검증을 다시 실행하고 RLS/DB 제약을 함께 적용해야 한다. 프런트 검사만으로 저장을 허용하면 안 된다.

## DB 연결 전 검토안 — 실행/생성하지 않음

### 필요한 이유와 기존 DB 관계

Auth는 비밀번호와 로그인 ID를 관리하지만 서비스 프로필·언어 정보·동의 이력을 저장하는 확인된 테이블이 소스에 없다.
총괄이 원격 기존 스키마를 먼저 확인하고, 기존 테이블을 재사용할 수 없을 때만 아래 구조를 검토한다.

### 제안 구조

`member_profiles` (가칭):

| 컬럼 | 제안 형식/제약 |
|---|---|
| user_id | uuid PK, auth.users(id) FK, on delete cascade |
| full_name | text, 1~100자 |
| phone_country_code | text, 국가번호 숫자 |
| phone_national_number | text, 숫자, 최종 정규화 정책 확정 필요 |
| nationality | ISO alpha-2 코드 |
| gender | female/male/undisclosed |
| birth_date | date, 미래 금지 |
| korean_level | 5단계 코드 |
| foreign_languages | jsonb 배열, 1~5개 {language,level}, 한국어 제외·언어 중복 금지·실력 검증 |
| created_at / updated_at | timestamptz, 서버 시각 |

이메일의 정본은 Auth에 유지하고 서버에서 사용자 정보와 함께 조회하는 안을 우선 검토한다.
프로필에 이메일 중복 저장이 필요하다면 Auth 이메일 변경과 동기화하는 방식까지 합의한다.
비밀번호·확인값·관리자 권한·운영진 내부 메모는 이 테이블에 두지 않는다.

`member_consents` (가칭):
user_id FK, policy_key, policy_version, required, accepted, accepted_at(서버 시각).
정책 버전별 수집 목적·항목·보관 기간·문서 스냅샷을 연결하고 필수/선택 동의의 변경·철회를 추적하는 구조를 총괄과 확정한다.
현재 코드나 문서에는 실제 동의 문구와 정책 내용을 임의로 확정하지 않았다.

### 제안 RLS/권한

- 비로그인은 프로필·동의 기록 조회 불가.
- authenticated 사용자는 auth.uid()=user_id인 본인 프로필만 조회·허용된 개인정보 컬럼 수정.
- user_id, 동의 버전, 동의 시각, 생성 시각은 일반 사용자가 임의 수정하지 못하게 컬럼 권한과 정책 분리.
- 직접 프로필 INSERT와 동의 이력 변경은 열지 않고, 승인된 가입 원자 처리에서만 생성.
- jsonb 외국어 제약도 DB에서 검사하여 우회 요청의 6개 이상·중복·미지원 코드 차단.
- 관리자 전역 프로필 조회는 이번 범위에서 부여하지 않는다.
- 기존 admin_users SELECT 정책과 관리자 수동 등록 절차는 유지한다.
- 개인정보 테이블을 Supabase Realtime 공개 채널에 연결하지 않는다.

### 계정만 생성되는 실패 방지

단순히 signUp 성공 뒤 별도 INSERT하는 방식은 이메일 인증 대기 시 세션이 없거나 INSERT가 실패하여 불완전한 회원을 만들 수 있다.
승인 후에는 Auth 사용자 생성과 프로필·동의 기록을 **하나의 DB 트랜잭션**에서 생성하는 트리거 방식을 우선 검토한다.
프로필/동의 검증·저장이 실패하면 Auth 사용자 INSERT도 롤백되어야 한다.

트리거는 새로운 사용자 생성 흐름에 영향을 주므로 기존 관리자 생성/초대 및 모든 가입 경로를 총괄과 점검해야 한다.
클라이언트가 자유롭게 설정하는 메타데이터 표식으로 필수 검증을 우회하게 만들면 안 된다.
프로필 전달에 Auth 메타데이터를 사용할 경우 개인정보 중복 보관·메타데이터 수정 가능성·삭제 정책도 별도 검토한다.
복구는 비밀번호/개인정보를 로그나 로컬 저장소에 남기지 않고 재시도 가능하게 설계하며 기존 이메일 계정에 임의로 프로필을 덮어쓰지 않는다.

중복 계정 판정이 불분명하면 계정 존재 여부를 확정하지 않는 일반 안내를 사용한다.
이메일 인증이 필요하면 안내와 검증된 확인 경로를 제공하고, 세션이 실제 생성된 경우에만 적절한 홈페이지 이동을 한다.
공개 가입 비활성·이메일 확인·비밀번호·메일 템플릿·허용 Redirect URL은 임의 변경하지 않는다.

### 총괄 확인/실행 순서

1. 원격 기존 프로필/동의 테이블·RLS·트리거·Auth 설정의 스키마만 확인.
2. 개인정보 항목별 필수성·수집 목적·보관 기간·동의 문구·문서 URL·버전 확정.
3. DB 구조·RLS·원자 생성·관리자 생성 흐름·복구 방안 검토 및 승인.
4. 별도 테스트 환경에 승인된 마이그레이션 적용 (이번 작업에서는 SQL 파일도 추가하지 않음).
5. 실제 가입 서버 Action에 기존 Supabase SSR 클라이언트와 공통 검증을 연결.
6. 동의/프로필 실패 롤백·타인 데이터 차단·이메일 인증·중복계정·기존 관리자 회귀 검증 후 활성화.

## 2026-10-15 선택지·헤더 후속 수정 및 저장값 호환성

외국어 입력의 none(전혀 못함)만 UI와 공통 검증에서 제외했다. 한국어 none은 계속 허용한다.
기존 입력 행 ID·추가/삭제·개별 상태 관리와 로그인·관리자 인증은 변경하지 않았다.
기존 DB 데이터는 조회·삭제·수정·마이그레이션하지 않았다.
원격 DB에 외국어 none이 저장되어 있는지는 미확인이다. 해당 값이 있다면 기존 기록은 그대로 보존하고,
향후 프로필 편집에서 같은 신규 입력 검증을 적용하기 전에 명시적 재선택/기존값 표시 정책을 확정해야 한다.
none을 basic으로 자동 변환하면 실제 실력과 다른 정보가 되므로 자동 변환하지 않는다.
현재 소스는 DB 저장을 연결하지 않은 입력 확인 화면이며 이번 수정에서도 그 상태를 유지했다.
