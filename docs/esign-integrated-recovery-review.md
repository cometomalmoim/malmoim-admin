# 19단계 가상 전체 통합·복구 검토

## 구현 범위
새 OfflineEsignIntegration은 development/test에서만 생성할 수 있는 서버 전용 통합 harness다. 실제 DB/Storage/SMS/OTP 클라이언트·환경변수·SQL을 추가하지 않았다. 운영 라우트와 기존 브라우저 시연을 교체하지 않는다. 기존 관리자/모바일/PDF 필드 편집·필터 CSS·신청자/이벤트/설문/수료증 코드는 유지한다.

## 실제로 연결한 흐름
관리자 이벤트 권한 → 정규화 복합 신청자 키 → EsignApplicantReader(16단계)의 일관 조회 계약 → signingEligibility → MemoryRequestRepository 요청 → SigningParticipantAuth(18단계) 링크·가상 OTP·요청 세션 → 인증된 원문 읽기 → requireSigningReady 필수/선택 응답·이름·서명 검증 → 서버 제출 접수 → createDemoDocument/completeDemoPdf의 원문 1페이지+완료 기록 1페이지 → EsignPdfStorage(17단계) 구조/해시 검증·readback → 저장 확인 후 요청 완료 → 관리자 권한 재확인 다운로드.

모든 원본은 명시적인 개발용 테스트 PDF다. 실제 업로드 원본·운영 서류 버전으로 위장하지 않는다. 게시 템플릿은 고정 테스트 서류이며 운영 템플릿 저장을 구현하지 않았다. 참가자 원문 읽기에는 기존 인증 Adapter의 authorize 메서드를 추가해 요청 전용 인증 세션을 재검증한다.

요청 식별자는 UUID와 (event_id,source,application_id)다. 문서 ID 기준 중복을 막고 동일 생성 operation 재시도는 기존 요청을 반환한다. 다른 대상에 동일 operation을 재사용하는 것은 차단한다. 연락처나 이름으로 신청자를 연결하지 않는다.

## 상태와 재시도
- 요청은 pending에서 시작한다. 인증과 필수 동의/서명을 서버가 검증한 후 job processing으로 진행하며 이때 다른 인증·중복 제출은 막는다.
- 서명 접수와 PDF 저장 완료를 구분한다. 서버가 검증한 제출 receipt는 Storage의 신뢰 입력이지만, 요청을 completed로 표시하는 것은 파일 readback·무결성·최신 상태 검사를 모두 통과한 뒤다.
- PDF 실패 시 요청은 완료되지 않고 job retry가 된다. 관리자 재시도는 기존 submission ID와 입력·한 번 생성된 PDF 바이트를 재사용한다. 참가자의 사용된 인증 세션을 다시 열거나 중복 제출을 만들지 않는다.
- 업로드 응답 유실은 Storage Adapter가 동일 경로 파일 readback으로 복구한다. 같은 경로 다른 내용은 덮어쓰지 않는다. 재시도 완료 후 반복 호출도 새 PDF를 만들지 않는다.
- 취소·상태/연락처/revision 변경·보관 변경 시 미완료 작업의 재시도는 차단한다. 원래 상태로 돌아왔더라도 revision이 달라지면 자동 재개하지 않으며 재검토가 필요하다. 완료된 파일은 권한 확인 후 조회할 수 있다.
- 업로드 성공 뒤 취소·보관·권한 변경이 감지되면 파일은 고아 객체가 될 수 있으나 완료 상태나 다운로드 권한을 부여하지 않는다. 자동 삭제·파기 정책을 임의로 만들지 않았다.

## 이벤트 보관 임시 정책
이벤트 id/archived/revision을 별도 서버 의존성으로 조회한다. 신규 요청, 링크 발급·재발급 시도, 인증/제출, PDF 생성·업로드 전후에 최신 상태를 검사한다. 보관된 이벤트의 신규 요청·재발급은 차단한다. 미완료 작업 처리 도중 보관되면 완료 확정도 차단한다. 완료 서류는 보관 후에도 관리자 이벤트 scope가 있으면 다운로드한다. 이것은 사용자 승인된 가상 시험 정책이며 운영 DB 정책으로 적용하지 않았다. 재발급 자체는 기존 정책 보류를 유지한다.

## 권한 검증 시점
생성 전후, 링크 발급, 제출 접수, PDF 생성/저장 전후, 관리자 상태 조회·재시도·취소·다운로드에서 AdminSessionAdapter를 검사한다. Storage Adapter도 다운로드 직전 권한을 재검증한다. 테스트의 admin 공급자는 통합 서버가 가진 권한 주체를 나타내며 실제 참가자 쿠키에서 관리자 세션을 조회하는 구현이 아니다. 운영에서는 요청 생성자/worker의 권한과 참가자 인증 주체를 분리해야 한다.

## 원자성 한계
서비스 직렬화 큐·repository transaction·auth store 큐는 한 프로세스 가상 시험의 중복 방지다. 조회·이벤트 공급자·PDF 생성·파일 저장·DB 완료를 묶는 실제 원자 트랜잭션은 아니다. 마지막 상태 재검사와 저장 사이의 외부 변경을 절대적으로 막는다고 주장하지 않는다. 운영에는 원자적 생성/접수/완료 RPC, revision CAS, 잠금 순서, durable job·lease·멱등 ledger가 필요하다. 인증 commit 응답 유실 후 영구 결과 조회·재시작 복구도 아직 없다.

## 실제 문자와 분리
통합 모듈은 실제 solapi/messaging/sms-worker 모듈을 import하지 않는다. OTP 제공자는 테스트에서 FakeSigningOtpProvider만 사용하며 inbox는 서버 테스트에서만 읽는다. 토큰·OTP·전화번호·서명 원문은 로그로 출력하지 않는다. 링크와 세션은 기존 18단계 해시 저장·기본 거부·제한 정책을 재사용한다. public API/쿠키/브라우저 OTP UI는 새로 연결하지 않는다. 기존 /preview/document-admin 및 /preview/sign/... 개발 코드는 이전 DEMO 가상 인증을 그대로 사용한다.

## 검증 시나리오
전체 Adapter를 연결한 테스트에서 정상 요청→OTP→원문→서명→2페이지 PDF→저장→다운로드를 확인한다. 추가로 중복 생성/동시 제출, 선택 동의 거절, 필수 동의/이름 오류, 합격 상태·참여 취소·전화번호·이벤트 보관/revision 변경, 인증 후 취소/만료, 완료 링크 재사용, PDF 생성/저장 실패·관리자 재시도·응답 유실·저장 hash 오류, 업로드 도중 권한/취소/보관 변경, 다른 이벤트 접근 차단을 시험한다. 개별 Adapter 테스트도 유지한다.

## 20단계 확인·승인 항목
1. API/UI에 새 흐름을 연결할지와 개발/운영 분리, HTTP 쿠키·CSRF·민감 로그·토큰 URL 처리 설계.
2. 실제 관리자/worker/참가자 인증 경계와 이벤트별 권한, 이벤트 보관·재발급·재서명·연락처 변경 정책 확정.
3. 별도 테스트 DB·키·RLS·private Storage·신뢰 가능한 문서/동의 버전 저장 승인. 운영 데이터/환경변수 복사 금지.
4. submission accepted와 PDF ready 상태의 DB 모델, 원자 RPC·job lease·멱등 결과·서버 재시작/다중 서버 복구.
5. 업로드 성공 후 DB 확정 실패·취소 경쟁의 고아 파일 추적/파기 및 완료 증적 불변성·보관 기간 승인.
6. 실제 업체 호출은 승인된 outbox 경로로만 연결하고 가상 OTP provider가 운영에 활성화되지 않게 검증.

이번 단계는 신규 서버 통합과 가상 테스트만 제공한다. 실제 운영 서비스 통합, 영구 저장, 실제 본인 확인이나 법적 증명 완료를 뜻하지 않는다.

## 이번 검증 결과
SQL을 실행하는 intake-db/sms-db 및 별도 DB 스크립트를 제외한 자동 테스트 350개 통과(신규 통합 16개 포함). 환경변수 없는 별도 복사본에서 TypeScript/프로덕션 빌드 통과, ESLint 오류 0·기존 suggestions 경고 2개. 기존 의존성을 재사용했으며 패키지 설치 없음.

127.0.0.1:3192 격리 서버에서 기존 관리자 요청 생성·링크 준비, 모바일 원문·동의 입력, 참가자 직접 화면의 가상 서명 제출·완료 PDF 표시, 관리자 완료 재조회·PDF 조회 링크를 수동 확인했다. 모바일 iframe의 일부 버튼은 자동화 도구가 클릭하지 못해 최종 제출은 같은 참가자의 직접 경로에서 확인했다. 디스크 다운로드 저장은 이번에 별도 확인하지 않았다. 이 수동 점검은 이전 시연 UI의 회귀이며 새 19단계 통합 UI를 제공한 것이 아니다. 기존 실행 서버는 종료·변경하지 않았다.
