## 범위와 적용

- `/admin/events` → 이벤트 등록 → `/admin/events/new`.
- 저장 후 `/admin/events/[slug]/overview`에서 확인, `/edit`에서 수정.
- 기존 `recruitment_events`를 확장한다. 기존 9기·신청자·자료 연결과 slug를 유지한다.
- 제목·소개·이미지 HTTPS 주소·행사 시작/종료·장소·정원·참가비 안내·모집 시작/마감. 일시는 한국시간 입력/표시, UTC 저장.
- 새 이벤트는 DB 기본값으로 draft/접수 비활성. 게시·접수 상태를 변경할 컬럼 권한을 부여하지 않는다.
- 기존 행에 새 일정이 없으면 미설정 표시. 수정 시 새 필수 항목을 입력해야 한다.
- 저장 실패 시 입력을 보존한다. 저장 성공 응답 이후에만 성공 안내와 상세 링크가 표시된다.
- 파일 업로드·회차 관리·페이지 빌더·접수·상태 변경은 후속 작업.

Supabase SQL Editor에서 `supabase/006_event_management.sql`을 검토 후 한 번 실행해야 한다. 003 적용이 전제다. 기존 행을 덮어쓰지 않으며 스키마 충돌은 transaction 전체를 중단한다. 이 작업에서는 운영 SQL을 실행하지 않았다.

적용 후 관리자 등록→목록→상세→수정→재조회, 기존 9기 신청자/자료 연결, 일반 회원·비회원 쓰기 차단을 확인해야 한다. 운영 데이터에 테스트 행을 임의로 생성하지 않는다.

## 1. 문제사항

행사 정보가 모집 페이지·신청 폼·운영 명단에 분산되어 같은 제목·일정·장소를 반복 입력할 가능성이 있다. 기존 도구와 실제 소요 시간은 사용자 조사 전이며 미측정이다.

## 2. 개선한 경험

이벤트 정보를 관리자에서 등록·조회·수정하는 첫 단계를 구현했다. 사용자 역할은 A조 이벤트 모집·운영 담당이다. 이번 세션에서 AI를 통한 구현을 진행했으며 개인 조사·운영 테스트·의사결정 기여는 실제 수행 근거가 쌓일 때 추가한다. 기존 홈페이지·인증·자료실 구현은 본인 신규 성과로 계산하지 않는다.

## 3. 진행 과정

사용자가 이벤트→모집 페이지→접수→신청자 조회 순서를 제시했다. 기존 DB와 관리자 조회를 조사하고 기존 테이블을 확장했다. 서버와 DB 권한을 함께 제한하고 모집 게시·접수 활성화는 분리했다. 기본 입력·시간대·일정 순서·정원·이미지 주소를 검증했다.

## 4. 측정할 수치

- 이벤트 1개 정보 등록 시간: 기존 미측정 / 개선 후 미측정. 동일 정보·기기·작업 범위로 추후 측정.
- 수동 복사·입력 횟수: 기존 미측정 / 개선 후 미측정. 모집 페이지와 연결된 후 동일 과업으로 비교.
- 자동 검증: 이벤트 입력 관련 테스트 4개 중 4개 통과. DB 저장·사용자 테스트 성공률을 의미하지 않는다.

시간 단축률은 `(기존 시간-개선 시간)/기존 시간×100`으로 계산하며 현재 계산할 근거가 없다.

## 5. 어려움과 해결 과정

기존 이벤트 테이블에는 제목·모집 상태·마감 위주 필드만 있었다. 별도 이벤트 테이블을 만들면 신청자·자료 연결이 분리될 수 있어 기존 테이블에 필드를 추가했다. 과거 이벤트는 새 필드가 비어 있어도 보존하고 수정할 때 입력을 요구한다. 한국시간 입력을 브라우저/서버 시간대로 해석하면 일정이 달라질 수 있으므로 +09:00으로 명시해 UTC로 저장하고 왕복 변환을 테스트했다.

## 6. AI 활용에서 좋았던 점

업무 요구를 등록·상세·수정 화면과 DB 확장으로 구체화하고 날짜·권한 등의 예외를 함께 검토했다. 사용자의 운영 검토와 실제 사용성 평가는 아직 진행하지 않았다.
