# 관리자 운영 조치 타임라인 정렬 수정

## 확인한 원인

1. `admin-board.tsx`의 기존 `LogList`가 신고 접수 행을 항상 첫 번째 `<li>`로 출력하고, 그 아래에 DB 로그를 붙였다. DB 로그만 최신순이어도 전체 타임라인은 최신순이 아니었다. 이는 앞선 관리자 화면 구현의 오류다.
2. 조치 로그 조회는 `created_at DESC, id ASC`였고, RPC로 읽는 게시글 상세 로그는 동일 시각의 보조 정렬을 보장하지 않았다. 렌더러에는 공통 정렬도 없었다.
3. 서버 액션이 `/admin/member-board`를 `layout`으로 재검증했다. 실제 라우트는 `/admin/[...segments]/page.tsx`이며 해당 위치에 member-board layout은 없다. 설치된 Next.js 가이드에 따라 실제 페이지 URL을 `type` 없이 재검증해야 한다.
4. 클라이언트 폼은 성공 응답을 받은 뒤 effect에서 `router.refresh()`를 별도로 실행했다. 서버 액션의 재검증 응답과 후속 경로 요청이 겹치는 두 단계 갱신이었다.

로그를 누적하는 클라이언트 상태나 별도 React 캐시는 없다. 로그는 서버 컴포넌트의 props로 렌더링되고, Supabase fetch는 `cache: "no-store"`이다. 따라서 확인된 문제는 DB에 저장된 순서/데이터의 손상이 아니라 접수 행의 별도 배치, 정렬 기준 부재, 잘못된 재검증 대상 및 중복 갱신 흐름이다.

**새로고침 관찰에 대한 한계:** 현재 소스에서 접수 행은 새로고침 후에도 항상 선두에 놓이므로, 사용자가 관찰한 “새로고침하면 정상화” 전체를 이 코드만으로 재현하거나 특정 캐시 경합으로 단정할 수는 없다. 수동 새로고침은 새로운 서버 응답을 받지만, 잘못된 접수 배치를 근본적으로 고치지는 않는다. 확인된 정렬 결함과 갱신 경로 결함을 모두 수정했으며, 실제 관리자 세션에서 운영 조치를 실행하는 재현은 운영 DB 변경 금지에 따라 수행하지 않았다.

## 해결 방식

- `member-board-timeline.ts`에서 접수 행과 조치 로그를 단일 배열로 합쳐 정렬한다. 접수는 실제 `board_reports.created_at`, 조치는 실제 `board_moderation_logs.created_at`을 사용한다.
- 시간대 오프셋을 반영한 epoch 시간으로 비교한다. Date.parse가 버리는 밀리초 이하의 소수부도 보존해 PostgreSQL의 마이크로초를 구분한다. 표시용 한국어 날짜/시각 문자열은 비교하지 않는다.
- 타임스탬프가 완전히 같으면 로그 ID 내림차순으로 고정한다. 접수와 조치가 같은 시각인 경우에도 종류와 ID로 결정적인 순서를 만든다.
- DB 쿼리는 `created_at DESC, id DESC`로 통일하고, 선택된 신고의 서버 응답과 공통 렌더러에도 동일한 정렬 함수를 적용한다. 게시글 상세의 운영 기록 역시 공통 렌더러를 사용한다.
- 입력 배열/객체를 변경하지 않는다. 접수는 신고 ID, 조치는 로그 ID로 각각 안정적인 React key를 지정한다. 다른 신고를 방문했다 돌아와도 이전 데이터나 DOM 순서에 의존하지 않는다.
- 서버 액션의 RPC 성공 이후 `/admin/member-board`와 영향받은 게시글 상세 URL만 실제 페이지로 재검증한다. 현재 필터와 선택 ID는 URL에 유지되므로 재검증 응답에서 목록/집계/패널/운영 기록이 다시 계산된다.
- 폼의 성공 effect에서 호출하던 `router.refresh()`는 제거했다. 상태·건수·기록을 갱신하기 위해 두 번째 경로 요청을 만들지 않는다. 기존 useActionState의 pending, 중복 제출 방지, 입력 유지 및 오류 안내는 유지한다.
- 선택 로그의 기존 최근 200건 제한을 유지했다. 추가 전체 로그 조회나 polling을 도입하지 않았다. 기존 신고 목록/결과 조회 구조는 유지한다.

## 이번 수정 파일

- `src/lib/member-board-timeline.ts` — 신규 공통 타임스탬프/보조 키 정렬.
- `src/lib/member-board-admin.ts` — DB 보조 정렬과 서버 로그 응답 정규화.
- `src/components/community/admin-board.tsx` — 접수·조치를 공통 타임라인으로 렌더링.
- `src/components/community/admin-moderation-form.tsx` — 중복 클라이언트 refresh 제거.
- `src/app/actions/community-board.ts` — 성공 후 실제 관리자 목록/상세 페이지 재검증.
- `tests/member-board-admin.test.mjs` — 정렬 및 갱신 흐름 회귀 테스트 추가.
- 이 결과 문서.

## 검증 결과

- `node --test tests/community-board.test.mjs tests/member-board-admin.test.mjs`: **31개 통과**.
- `npm run lint`: 성공. 기존 suggestions.ts의 미사용 인자 경고 2개만 남아 있다.
- `npm run build`: 성공. 기존 Node 20에 대한 Supabase 지원 중단 예정 경고는 유지된다.
- `git diff --check`: 통과.

추가 회귀 테스트는 다음을 검증한다.

1. 접수 20:00, 검토 21:09:01, 숨김 21:09:50, 종료 21:10을 섞인 입력에서도 최신순으로 렌더링한다. 접수 이전 조치가 있는 경우에도 실제 시간대로 배치한다.
2. 서로 다른 시간대 표현, 동일 밀리초 내 마이크로초 차이, 완전히 같은 타임스탬프의 ID 보조 정렬을 구분한다.
3. 다른 신고 선택 후 복귀 및 새 요청에서 정렬 결과가 같고 원본 응답 배열을 수정하지 않는다.
4. 선택 로그의 200건 제한과 DB의 `created_at DESC, id DESC`를 유지하며 서버 응답을 정렬한다.
5. 실제 클라이언트 폼의 action 콜백 → 서버 액션 → 모의 RPC 성공 → 페이지 재검증 → 서버 컴포넌트 렌더링 흐름에서 처리 상태, 미처리 건수, 선택 패널, 타임라인이 갱신된다. 처리 완료로 현재 필터의 목록에서 빠진 신고도 선택 패널에는 최신 상태로 남는다. 추가 client refresh는 실행하지 않는다.

이 테스트는 운영 DB가 아닌 메모리 데이터/모의 세션에서 실행했다. 실제 Next.js 브라우저 Flight 응답과 운영 관리자 세션의 쓰기 동작을 직접 재현하는 E2E 테스트는 아니다. 운영 로그/상태/테이블/SQL/RLS/인증은 변경하지 않았다.
