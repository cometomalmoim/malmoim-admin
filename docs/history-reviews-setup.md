# 참여 후기 게시판 연결 (승인 전 SQL 제안)

## 현재 상태와 수정 범위

`/history` 전용 파일에서 기존 Supabase SSR 클라이언트와 `auth.getUser()`를 재사용합니다. 서비스 역할 키를 사용하지 않습니다. 갤러리·활동 필터·공통 인증·헤더·다른 페이지는 변경하지 않습니다.

`supabase/003_history_reviews.proposed.sql`은 운영 적용 전 검토용 제안입니다. 운영 후기 테이블·버킷은 아직 미적용이며 이번 작업에서도 운영 DB·Storage에 접근하지 않습니다. 로컬에는 테이블·RLS 4개·비공개 버킷·Storage 정책 3개를 생성했고, A/B·anon 역할과 `auth.uid()`를 재현한 후기 테이블 권한 검증을 통과했습니다. 실제 Storage 업로드 권한과 새 사진 처리 기능의 로컬 통합 검증은 별도입니다. 테이블이 없거나 DB 조회가 실패하면 목록에 연결 오류를 표시하고 저장 성공을 표시하지 않습니다.

**새 설계: 원본 선택 5MB / 압축 후 저장 1MB / 최대 3장.** 이 문서와 SQL 초안 변경은 기존 로컬 버킷 설정을 바꾸지 않습니다. 현재 로컬 버킷은 이전 200KB 제한이므로, 200KB 초과 결과물을 실제 업로드하기 전에 설계 승인 후 해당 버킷 한 개의 크기 제한을 1,048,576바이트로 변경해야 합니다. 기존 로컬 테이블이 있으므로 생성 SQL 전체를 다시 실행하지 않습니다. 로컬 테스트 서버 `3001`은 임시 소스 사본이므로 새 코드를 반영한 별도 실행도 필요합니다. `.env.local` 및 배포 환경변수는 변경하지 않습니다.

## 승인 및 적용 대상

DB 관리자의 검토·승인 후 올바른 Supabase 프로젝트 SQL Editor에서 제안 SQL을 적용합니다. 새 `public.history_reviews` 테이블, 인덱스 2개, 검증 함수·트리거, 테이블 RLS 정책 4개, 비공개 `history-review-photos` 버킷, 해당 버킷의 Storage 정책 3개가 필요합니다. 기존 스키마나 버킷 설정은 변경하지 않습니다. 같은 이름의 객체가 있으면 먼저 비교하고 SQL을 조정해야 하며 자동 덮어쓰기는 하지 않습니다.

1. 기존 `storage.objects`의 RLS 활성화와 정책을 확인합니다. 기존 광범위한 허용 정책은 OR로 합쳐지므로 새 버킷을 포함하지 않도록 관리자가 검토해야 합니다. 이 제안은 기존 정책을 임의 수정하지 않습니다.
2. 후기는 비로그인 방문자도 읽을 수 있는 공개 게시물입니다. 본문·표시명·사진 공개 방침을 확인합니다. 이메일은 노출하지 않으며 `user_metadata.display_name`이 없으면 `익명`으로 표시합니다. 표시명은 검증된 실명이 아닙니다.
3. SQL을 트랜잭션으로 실행합니다. 충돌·오류가 발생하면 롤백하고 원인을 확인합니다. 원격 DB 연결 환경변수는 기존 `.env.local` 설정을 재사용합니다. 비밀 값은 공유하지 않습니다.
4. `/history`를 새로고침해 연결 안내가 없어지고 실제 빈 목록이 나오는지 확인합니다.
5. 아래 계정별 검증을 수행한 후 배포합니다. SQL만 적용해 실제 검증을 완료했다고 판단하지 않습니다.

## 동작과 제한

- 전체/정규 세션/특별 활동/기타로 DB에서 필터링하고 최신순으로 6개씩 조회합니다. 상세는 카드에서 네이티브 dialog로 열립니다. Escape, 키보드 포커스 제한과 복귀를 지원합니다.
- 신규 등록은 카테고리 3개, 제목 120자, 내용 10,000자 제한입니다. 서버가 세션에서 author_id를 정하고 수정·삭제는 author_id 조건과 RLS를 모두 거칩니다. DB는 작성자·작성일·표시명 변경도 금지합니다.
- 후기의 로그인 안내는 일반 회원 로그인 `/auth/login`을 사용합니다. 관리자 로그인 `/login`과 구분합니다. 현재 회원 로그인 성공 시 한국어는 `/`, 영어는 `/en`으로 이동하며 이 동작은 변경하지 않았습니다. `/history` 자동 복귀나 `?next` 처리는 없으므로 로그인 후 사용자가 후기 페이지로 돌아와야 합니다. `/history`는 현재 `src/proxy.ts`의 세션 갱신 대상에 포함되어 있습니다. 새로운 인증·회원가입 기능은 추가하지 않습니다.
- 원본 선택은 JPG/PNG/WebP 각 5MB(5,242,880바이트), 기존 사진 포함 최대 3장입니다. 원본은 업로드하지 않고 브라우저에서 방향을 반영해 캔버스에 다시 그립니다. 긴 변 최대 1600px로 축소하며 작은 이미지는 확대하지 않습니다. WebP 품질 0.86부터 시도하고, 필요할 때 0.80·0.74 및 긴 변 1440·1280px을 시도합니다. 품질 수치는 브라우저별 결과가 다르며 모든 파일의 1MB 이하 변환을 보장하지 않습니다. 한도에 맞추지 못하면 사진을 첨부하지 않고 안내하며, 지나치게 낮은 품질이나 원본 업로드로 우회하지 않습니다.
- 저장 결과는 각 1MB(1,048,576바이트) 이하, 3장 합계 최대 3MiB입니다. 현재 Server Actions 요청 본문 제한은 `experimental.serverActions.bodySizeLimit: '5mb'`입니다. 처리된 파일과 본문·multipart 부가 정보를 합쳐도 여유가 있어 공통 설정은 변경하지 않습니다. 서버에서 새 첨부 개수·빈 파일·실제 바이트 크기·MIME와 JPEG/PNG/WebP 헤더 일치를 확인하고, 기존 사진 포함 3장도 검사합니다. SQL 초안의 비공개 버킷도 동일한 1,048,576바이트와 MIME 3종을 사용합니다.
- WebP 인코딩은 `toBlob()`의 실제 반환 MIME로 지원 여부를 확인합니다. 지원하지 않으면 픽셀의 투명도를 확인해 불투명 사진은 JPEG, 투명 사진은 PNG로 변환합니다. 흰 배경으로 강제 합성하지 않습니다. `createImageBitmap` 실패/미지원 시 이미지 요소를 사용하며 원본 EXIF 방향을 브라우저 디코더에서 반영합니다. 사진은 한 장씩 처리하고 비트맵·Object URL·캔버스 메모리를 해제합니다. 처리 중 저장·중복 선택을 막고 실패 시 본문과 기존 첨부를 유지합니다.
- 새 캔버스 결과물에는 원본 EXIF/GPS·촬영 정보·원본 파일 바이트를 복사하지 않습니다. 브라우저가 새로 생성하는 DPI 등은 남을 수 있습니다. 이 처리는 정상 후기 업로드 경로 기준이며 서버의 파일 헤더 검증이 모든 메타데이터 검사나 완전한 이미지 디코딩을 대신하지는 않습니다. Storage API로 직접 올리는 파일의 메타데이터까지 강제 제거하려면 서버 전용 이미지 처리 경로와 Storage 쓰기 정책을 별도로 검토해야 합니다. 이번에는 인증·RLS·업로드 경로를 변경하지 않습니다.
- 원본 파일명 대신 사용자 UUID/후기 UUID/무작위 UUID로 저장합니다. 비공개 버킷의 사진은 1시간 signed URL로 표시하므로 오래 열린 페이지는 새로고침이 필요합니다. 이미 발급한 URL은 만료 전까지 유효할 수 있습니다.
- 수정 시 기존 사진 유지·선택 삭제·추가를 지원합니다. DB 저장 실패 시 새 업로드를 정리하며, 삭제 후 파일 정리 실패는 별도 안내합니다. DB와 Storage는 단일 트랜잭션이 아니므로 네트워크 단절·계정 삭제 등에 따른 고아 파일은 관리자가 점검해야 합니다. 같은 글 동시 수정은 마지막 저장 기준입니다.
- 사진 없는 게시물은 Storage 요청 없이 조회·저장됩니다. 사진 기능은 버킷 및 정책 적용 후 사용 가능합니다.

## 실제 계정으로 수행할 검증

- 비로그인: 공개 목록·카테고리·상세, 등록 버튼의 로그인 안내. 직접 서버 액션 또는 DB INSERT/UPDATE/DELETE 요청도 거부되어야 합니다.
- 계정 A: 필수값/공백/길이 검증, 실제 등록 성공 후 새로고침 유지, 제목·본문·작성일·표시명·대표 사진 확인, 수정·사진 삭제 및 추가, 취소, 삭제 확인 및 실제 삭제.
- 계정 B: A의 수정/삭제 버튼 미노출. DB/API에서 A의 id를 사용한 수정·삭제는 0행 또는 거부, author_id 바꾸기와 타인 경로 사진 업로드·삭제 거부. 자기 글 작성과 수정은 허용.
- 원본 5MB 초과·빈 파일·잘못된 형식, 처리 결과 1MB 초과·MIME/헤더 불일치, 4장 및 기존 사진 포함 4장 거부. 원본 크기 경계, 세로 EXIF 사진 방향, 투명 PNG/WebP, WebP 인코딩 미지원 시 JPEG/PNG 대체, 순차 처리·중복 선택·처리 중 저장 방지·실패 후 본문 유지·미리보기 취소도 확인합니다. 업로드/DB 장애 시 저장되지 않은 성공 메시지가 없어야 합니다.
- 실제 테스트 후기가 7개 이상인 환경에서 더 보기, 필터 전환 후 목록 초기화와 중복 없는 페이지 확인. 가짜 운영 데이터를 생성하지 않습니다.
- 375px/768px/데스크톱 화면, Tab/Shift+Tab/Escape 및 모달 종료 후 초점 복귀. 기존 갤러리 정규 세션/특별 활동 및 기수·연도 필터 회귀 확인.

## 사진 제한 개선의 검증 범위

- 코드·입력 안내·SQL 초안은 위의 새 저장 기준으로 변경합니다. 로컬 버킷 설정은 설계 승인 후 별도 적용하며 운영 DB·Storage는 변경하지 않습니다.
- `node --test 'src/app/(public)/history/review-photo.test.mjs' 'src/app/(public)/history/review-store.test.mjs'`: 21개 통과. 원본 5MiB 경계, 처리 결과 1MiB 경계, 형식 위장·잘린 헤더·빈 파일·파일 아닌 첨부·4장·기존 첨부 포함 초과 거부, 제한된 품질/크기 재시도, Storage 실패와 signed URL 일부 실패 격리를 확인했습니다. 서버 동작은 모의 클라이언트로 검사했으며 실제 업로드 검증을 의미하지 않습니다.
- 별도 Chrome의 합성 이미지 검사 7개 통과. EXIF 방향 6을 넣은 JPEG 3,546,134바이트를 1200×1600px WebP 981,854바이트로 처리했고 원본 EXIF 미포함을 확인했습니다. 투명도·작은 이미지 비확대·WebP 입력·WebP 인코딩 미지원 시 JPEG/PNG 대체·5MiB 초과 거부도 확인했습니다. Safari 대체 경로는 모의 환경과 Chrome에서 재현했으며 실제 iPhone Safari 검사와 구분합니다.
- 환경변수 파일 없는 임시 소스 사본의 개발 미리보기를 별도 Chrome에서 1280px·390px로 검사했습니다. 실제 파일 선택 이벤트 후 압축·미리보기, 처리 중 저장 차단, 첨부 취소, 5MiB 초과·4장 거부, Escape 유실 확인 후 계속 작성 시 첨부 유지, 가로 넘침 없음을 확인했습니다. DB/Storage 요청 및 변경 요청은 0건이었습니다.
- `npm run lint`: 오류 0개, 기존 다른 파일 `src/app/actions/suggestions.ts`의 미사용 인자 경고 2개. 해당 파일은 수정하지 않았습니다. `npm run build -- --webpack`: TypeScript 포함 통과. 빌드 프로세스에 루프백 설정을 주입하고 운영 설정을 덮어써 원격 Supabase 접근을 방지했으며 환경변수 파일은 수정하지 않았습니다.
- 로컬 실제 업로드·사진 수정/삭제·signed URL 권한, 모바일 Safari 실기기 검증은 버킷 설정과 새 테스트 서버 반영 후 확인해야 합니다.
