# 관리자 회원 게시판 개편 결과 — 2026-10-20

## 1. 기존 구현 분석

`ProtectedAdmin`은 기존 Supabase Auth 및 `admin_users` 허용 목록을 확인한 뒤 `/admin/member-board`를 `CommunityRoute`로 연결한다. 내부 운영 게시판은 `/admin/internal-board`로 별도 유지된다. 기존 회원 게시판의 관리 목록은 공개 게시판 컴포넌트를 관리자 모드로 재사용했고, 신고 조회는 개별 게시글 상세에서만 가능했다. 상세에 숨김, 고정, 댓글 처리, 신고 처리 폼이 반복되는 구조였다.

설치된 Next.js의 loading/Suspense 및 useRouter 문서를 확인했다. 인증 경계와 `AdminShell`의 사이드바·헤더를 유지하고, 인증 이후 관리자 전용 컴포넌트로 분기했다. 사용자 게시판과 앞선 UI 변경은 보존했다.

DB에 지원되는 신고 상태는 `pending`, `reviewing`, `resolved`이다. 신고자 UUID를 제외하는 상세 RPC에는 신고자의 공개 별칭이 없다. 운영 기록의 처리 관리자는 UUID로 제공되며 이메일/이름 변환은 제공되지 않는다. `board_aliases`에는 일반 클라이언트의 직접 조회 권한이 없다.

## 3. 새 관리자 페이지

- 상단 제목/설명과 공지사항 작성 버튼.
- 전체 게시글, 미처리 신고(대기+검토), 숨김 게시글, 상단 고정 게시글의 실제 count 지표. 각 지표는 대응 목록/필터로 이동한다. 삭제 글은 고정 지표에서 제외하며 숨김 고정 글은 포함한다.
- 지표 조회 실패 시 `조회 불가`와 오류 안내를 제공한다. 실패를 0건으로 대체하지 않는다.
- 게시글 목록 / 신고 내역 / 숨김 게시글 / 공지사항 네 탭.
- 지표·목록·신고 패널·게시글 상세에 Suspense 스켈레톤. 공통 관리자 헤더를 중복 생성하지 않는다. 인증 전에는 기존 접근 권한 확인 화면을 유지한다.

탭 이동 시 검색어/검색 범위/기간/작성자 조건은 유지하고, 탭별 카테고리·공개 상태·고정·신고 상태·처리 결과·대상 조건과 페이지/선택 항목은 초기화한다. 숨김 탭과 공지 탭은 각각 숨김 상태와 공지 카테고리를 강제한다. 필터 검색은 선택/페이지를 초기화한다.

## 4. 신고 내역 전용 탭

실제 `board_reports`와 관련 `board_posts`/`board_comments`를 기존 인증 세션으로 조회한다. 서비스 역할 키를 사용하지 않는다. 서버 관리자 검사와 기존 RLS 모두 적용된다.

처리 상태, 대상 유형, 카테고리, 관련 제목/신고 당시 내용 요약, 신고 사유, 대상 작성자 별칭, 접수일, 상세 링크를 표시한다. 미처리 우선·최신순이며 20건 단위 페이지를 제공한다. 상태/대상/카테고리/기간/검색 범위/검색어/조치 없음 결과로 필터링한다. 빈 결과와 DB 오류를 구분한다.

원래 RPC에 전체 신고 목록 조회가 없어 직접 읽기를 추가했다. 상태/대상 조건은 DB에 적용하고, 결합된 카테고리/원문/별칭/기간/처리 결과 조건은 서버에서 적용한다. Supabase 기본 행 제한에 걸려 신고를 누락하지 않도록 500건씩 끝까지 읽은 후 필터와 페이지를 계산한다. 이 구현은 DB 변경 없이 정확한 목록을 제공하지만 신고·로그가 매우 많아지면 조회 비용이 증가한다. 대용량에서는 관리자 전용 필터/집계/페이지네이션 읽기 RPC로 옮기는 개선이 권장된다.

## 5. 신고 상세 및 처리 흐름

선택된 행을 강조하고 우측에 기본 정보, 당시 원문, 현재 원문/상태, 신고 이유, 운영 조치, 최근 대상 조치 200개를 표시한다. 선택 ID가 URL에 저장되며 목록 필터/페이지를 보존한다. 처리 후 현재 목록 조건에서 사라져도 선택된 신고를 별도로 조회해 결과를 확인할 수 있다. 닫기는 선택 ID만 제거한다.

모바일은 전체 화면 패널이며 배경 스크롤 잠금, 진입 포커스, Tab 순환, Esc 닫기를 제공한다. 데스크톱/태블릿은 화면 폭에 따라 우측 패널 또는 단일 컬럼을 사용한다.

조치는 선택 상자 하나, 처리 사유 입력 하나, 실행 버튼 하나로 구성한다. 실행 전 선택한 조치를 확인하고, 저장 중 전체 폼을 비활성화한다. 즉시 중복 제출을 막으며 성공 후 동일한 제출의 반복을 제한한다. 오류/통신 실패 시 제어 입력값을 유지하고 오류 메시지를 표시한다. 성공 시 기존 경로 재검증과 router.refresh로 지표·목록·선택 패널을 갱신한다.

댓글 신고에는 해당 댓글의 숨김/복구만 제공한다. 부모 게시글 숨김 옵션은 없다. 게시글 신고에는 게시글 조치를 제공한다. 삭제된 대상에는 숨김/복구를 제공하지 않는다. 댓글이 공개여도 상위 게시글이 숨김이면 이를 별도로 안내한다.

기존 RPC에서 원문 숨김/복구와 신고 상태 변경은 각각 독립된 작업이다. 화면에서도 `숨김 (신고 상태 유지)`, `처리 완료 (원문 상태 유지)`로 구분한다. 숨김 후 검토를 마쳤으면 같은 사유 입력을 재사용해 별도로 종료한다. 두 작업이 원자적으로 함께 처리됐다고 표시하지 않는다. 신고 처리에 따른 원문 자동 삭제는 없다.

## 6. 게시글 목록/상세

목록은 제목 중심이며 UUID는 펼칠 수 있는 보조 정보로 이동했다. 공개/숨김/삭제 배지, 고정 여부, 작성자/날짜/조회/댓글, 상세/공지 수정 링크를 제공한다. 숨김 탭에는 최신 숨김 사유·관리자 ID·처리일을 표시하고 로그 조회 실패도 구분한다.

상세는 원문·댓글을 본문에, 운영 조치·관련 신고·접을 수 있는 운영 기록을 옆에 배치했다. 숨김/복구/고정/해제도 하나의 선택 폼을 사용한다. 댓글별 숨김·복구는 접을 수 있는 짧은 폼으로 제공한다. 댓글 검색·페이지 이동·등록을 유지했다.

일반 회원 글에는 관리자 본문 수정/삭제 버튼을 표시하지 않는다. 기존 DB의 공지사항 수정 권한이 있는 경우에만 공지 수정/삭제가 표시된다. 새 공지 작성/수정은 기존 폼과 서버 액션을 유지한다. 일반 게시글과 공지 모두 여러 개를 고정할 수 있으며, 실제 공개 목록의 제외 정책은 기존 RPC/RLS에 따른다.

## 7. 기존 RPC 재사용

- 게시글 목록: `member_board_list`.
- 게시글/댓글/신고/이력 상세: `member_board_detail`.
- 모든 저장: 기존 `mutateCommunity` 서버 액션 → `member_board_mutate`.
- 공지 작성자/수정 권한 확인: 기존 `member_board_can_change`.
- 전체 신고 피드와 추가 통계만 기존 테이블의 허용된 읽기 권한을 사용한다.

새 SQL, 테이블, 상태 코드, RLS, 인증 설정은 추가/변경하지 않았다.

## 8. 권한/기능 보호

관리자 페이지와 새 조회 함수에서 서버 관리자 확인을 수행한다. 저장은 기존 서버 액션의 인증/관리자 검사와 DB RPC의 관리자 검사, 대상 ID/버전 검증을 그대로 거친다. 조치 사유와 관리자 이력도 기존 저장 구조를 따른다.

신고자 UUID/이메일/전화번호는 조회하지 않는다. 신고자 영역에는 `공개 식별 정보 미제공`을 표시한다. 대상 작성자는 기존 공개 별칭, 처리 관리자는 기존 운영 기록의 실제 계정 ID로 표시한다. 임의 별칭이나 관리자 이메일을 합성하지 않는다.

## 10. 실제 DB에서 남은 확인

관리자 로그인 후 읽기 검증: 실제 지표/신고 목록, 운영 DB의 FK 관계 조회, 카테고리/기간/검색 필터, 선택 패널, 신고 당시 원문/현재 상태/운영 로그, 숨김 기록.

별도 승인 후 쓰기 검증: 공지 작성/수정, 게시글·댓글 각각의 숨김/복구, 고정/해제, 검토/완료/조치 없음 종료, 성공 후 필터·패널·지표 갱신, 오래된 버전 오류, 네트워크 실패 후 사유 유지. 비관리자 실제 세션의 DB 접근 거부도 별도 세션으로 확인할 필요가 있다.

## 11. DB 확장이 필요한 기능

- 독립적인 `rejected`/`no_action` 상태: 현재 CHECK/RPC가 허용하지 않는다. 이번 구현은 `resolved`와 로그 사유의 `[조치 없음] ` 접두어를 사용한다. 기존 완료 기록의 결과를 추정하지 않는다.
- 구조화된 처리 결과/보고서용 통계: 사유 접두어 대신 별도 결과 필드가 필요하다.
- 신고자 공개 별칭: 현재 RPC와 읽기 권한이 제공하지 않는다. Auth UUID를 노출하지 않는 검토된 조회 API가 필요하다.
- 독립 운영 메모/담당자 배정: 현재 컬럼과 저장 작업이 없다. 현재는 실제 조치 시 입력한 사유만 운영 기록으로 저장한다.
- 원문 조치와 신고 종료의 단일 원자적 저장: 기존 RPC는 둘을 함께 처리하지 않는다. 결합된 트랜잭션 작업을 지원하는 RPC 확장이 필요하다.
- 대용량 신고 목록의 DB 측 결합 검색/정렬/페이지/결과 집계: 관리자 읽기 RPC가 권장된다.

## 12. 권장사항 / Git

현재 구현의 다음 단계는 실제 관리자 세션에서 읽기를 검증하고, 승인된 별도 테스트 대상으로 쓰기 흐름을 확인하는 것이다. 이후 신고량이 커지면 목록 읽기를 전용 RPC로 옮기고 구조화된 처리 결과/운영 메모를 검토할 수 있다.

`feat/website-yukyung`을 유지했다. 기존 미완료 변경을 보존했으며 새 브랜치/커밋/push/SQL 변경은 없다. 최신 origin/main은 fetch했지만 이번 커밋 금지와 앞선 자동 승인 검토 결과에 따라 병합하지 않았다.
